# ADAM device reference corpus for Amy EOS backends

Status: investigation index  
Source inventory: `build/audits/adam-media-corpus.json`

Executable triage: `build/audits/adam-eos-candidates.md`, generated by
`tools/rank-adam-eos-candidates.mjs`. Its scores are heuristic and only select
targets for extraction and runtime tracing; they are not compatibility claims.

## Method

Real ADAM software is used to discover stable device behavior that is missing or
ambiguous in manuals. It is evidence, not source material for direct reuse.

For each selected program Amy Studio will record:

1. boot memory configuration and EOS revision assumptions;
2. EOS and AdamNet entry points called;
3. device IDs and device-control-block layouts;
4. input, output, status, timeout, and retry conventions;
5. RAM buffers and interrupt ownership;
6. behavior when the expected device is absent;
7. an equivalent minimal Amy operation and GearColeco test.

SmartBASIC and CP/M applications remain out of scope as Amy runtime targets, but
their machine-code helpers may corroborate hardware protocols when identified
independently.

## Evidence levels

| Level | Requirement |
| --- | --- |
| `IDENTIFIED` | Relevant file and media are known. |
| `TRACED` | Calls, device IDs, buffers and status transitions are recorded. |
| `REPRODUCED` | A minimal standalone assembly test reproduces the behavior. |
| `AMY COMPILES` | Target-specific Amy lowering assembles without OS-7 dependencies. |
| `AMY VERIFIED` | GearColeco test confirms the expected device behavior and failure path. |

No command enters the public native-EOS support matrix as `VERIFIED` until the
last level is reached. Existing OS-7 output and ROM sizes remain a separate,
unchanged regression gate.

`VERIFIED` for `AdamNetPcb`/`AdamNetDcb` must not be read as verification
of every possible AdamNet device. It proves the records and generic submission
mechanism against known completion and absent-device responses `$96/$9B`;
their association with one particular medium is not stable after EOS updates
the active DCB table. Successful
device-specific protocols still require their own runtime evidence. Native DSK
and DDP tests cover `$96/$9B` responses, and a separate real OS7+EOS hybrid disk
test covers an absent-device response while proving that execution continues.

## First executable trace: ModemTank

`ANN Disk - 1999-02b - E.O.S. Files.dsk` contains an executable ModemTank set:
`BOOT` (1 KiB), `Tank` (36 KiB), and `TANKPIC` (6 KiB). The similarly named
`ModemTankA` file is an article, not the executable.

An 1,800-frame GearColeco execution trace establishes that the observed boot,
loading, title, and keyboard path uses EOS rather than OS-7:

- `FC30` initializes EOS;
- `FCC0`, `FCD2`, and `FCC3` open, read, and close files;
- `FCF0` searches the active file-control blocks;
- `FC36` initializes the console window;
- `FC39` performs special console output;
- `FC6C` performs a blocking ADAM keyboard read;
- `FCA8` and `FC4B` start and complete an asynchronous keyboard read;
- `FD3E` polls the ColecoVision controllers during local play;
- `$FD11-$FD59` provide memory switching, VDP, ASCII, and sound services.

No OS-7 service breakpoint was reached in that path. This turns ModemTank into
a concrete pure-EOS reference for Amy's file, console, keyboard, graphics, and
sound backends. Selecting the ADAM smart key `IV` reaches local gameplay and
proves that a native EOS game can use the full ADAM keyboard and ColecoVision
controllers together. Modem communication itself still needs a trace that
selects one of the three hardware interfaces and records either DCB/AdamNet
transactions or direct expansion-port I/O.

The reproducible tracer is `tools/trace-adam-firmware-services.mjs`. It covers
every stable EOS vector from `$FC30` through `$FD5C`, records the first CPU and
AdamNet context for each service, and deliberately leaves unverified vectors
named by address rather than guessing their purpose.

Both `tools/capture-adam-disk.mjs` and the service tracer accept repeatable
scripted key events through `--adam-keys=frame:key,...`. The key number is the
stable `GC_AdamKey` enumeration; for example smart key IV is `56`. This makes
interactive EOS paths reproducible rather than dependent on manual timing.

Direct serial-port findings are maintained in
`docs/adam-modem-interface-map-2026-09-30.md`. ModemTank distinguishes AdamLink,
Orphanware/Eve, and MicroInnovations hardware; these are direct-I/O serial
backends rather than ordinary AdamNet block devices.

## Independent terminal reference: ADAMLink III

`ANN Disk - 2024-04 - AdamLink III.dsk` contains a 21 KiB `ADAMLINK`
executable and an XMODEM patch document. Its observed terminal screen uses the
ADAM smart keys, and an idle 1,200-frame trace repeatedly completes asynchronous
keyboard reads through `$FC4B` after starting them through `$FCA8`. It also
calls `$FC93` to release keyboard lock/modifier state before interactive input.

Static I/O evidence independently finds repeated reads and writes at `$5E` and
`$5F`, corroborating the Orphanware/Eve port family found in ModemTank. The
documentation describes XMODEM send/receive integrated with EOS disk or Data
Pack files, including cancellation and partial-file preservation. A scripted
runtime probe now proves that Wild Card reaches AdamLink's actual `CP $90`
dispatch and that Smart Keys I-VI produce VRAM changes distinct from a
deterministic no-key control. Wild Card itself does not change VRAM or VDP
registers in that state; an earlier fixed-frame capture had incorrectly
attributed a later mode transition to the key. The state-driven trace now maps
Smart VI to FILE state `$10`, Smart III/IV to the XMODEM send/receive choices,
and the following drive selector to state `$01`; Smart III there selects DISK I
and reaches filename-entry state `$0B`. Completing filename/type entry requires
observing expansion RAM while AdamLink temporarily maps it through MIOC, which
the current post-frame RAM reader cannot expose. The actual packet transfer
therefore remains unverified.

The 2024 ANN archive was re-opened directly rather than relying on the earlier
extraction. Its EOS directory reports `ADAMLINK` as a 21-block/21,504-byte
executable and `ALink3_DocA` as a 2,560-byte document. The executable contains
two reads and two writes at `$5E`, seven reads and thirteen writes at `$5F`;
the document explicitly identifies the XMODEM patch and its EOS disk/Data Pack
workflow. This is strong protocol-discovery evidence, but still not emulator
execution evidence for the absent serial card.

## Chess Champ expansion-RAM loader display

`Chess Champ (1988) (Digital Express Inc.) [ExpRAM].dsk` exposes a loader
compatibility case rather than a default-register defect. At frame 81 the
loader enables Graphics I with registers `00 E0 02 2C 00 00 00 0E`, selecting
NAME `$0800`, COLOR `$0B00`, PATTERN `$0000`, and sprite attributes `$0000`.
The pattern and sprite-attribute tables therefore overlap, and the program
does not place a `$D0` terminator in the sprite list. A strict TMS9918A renderer
interprets pattern bytes as sprite attributes and draws stray glyphs over the
otherwise correct title.

ADAM+ independently handles this class of old software by terminating the
current sprite list after an ADAM mode transition. GearColeco now applies a
narrow equivalent compatibility rule during the first 180 ADAM startup
frames: only after display becomes active, only on the TMS9918A backend, only
when PATTERN and sprite-attribute bases are identical, and only when all 32
sprite entries lack a terminator. Normal ColecoVision rendering and valid ADAM
sprite lists are unchanged. The TMS9918A renderer also uses the hardware sprite
height when deciding whether encoded Y coordinates wrap above the screen.

`tools/test-chess-champ-adam-compatibility.mjs` keeps the proprietary DSK
external, verifies the inserted `$D0`, pins the clean title framebuffer, waits
through its timed presentation, and confirms that the later chess display is
byte-for-byte unchanged. `tools/capture-adam-disk.mjs` reports every VDP
register transition and can dump RAM/VRAM for similar investigations.

## Printer and serial triage

The files `PRINTERA`, `printertipA`, `PRINTERFANH`, and `PRINTERFIXA` were
extracted and inspected. They are articles and repair notes, not executable
printer implementations. They must not be used as runtime evidence.

`SWriter2` on `ANN Disk - 2019-06 (2).DSK` is a 32 KiB electronic typewriter
with print options. Its executable contains a concrete port sequence using
`$5E` for output and `$5F` for status input, matching the independently traced
AdamLink interface. Under the current GearColeco build it loads
but remains on a blank blue display in its initialization delay. This is a
useful failure-path fixture for the missing optional serial-device emulation.

The stock SmartWriter firmware supplies the separate AdamNet printer proof.
After 180 emulated frames it has written ten bytes to device `$02` (`CR`
followed by nine spaces). `tools/test-gearcoleco-adam.mjs` verifies those bytes,
then clears and rereads the spool through the WebAssembly test bridge. This
confirms GearColeco's printer command path independently of the serial-card gap.

EOS vectors `$FC63` and `$FC66` are now independently reproduced by the native
EOS starter. `$FC63` accepts an ETX-terminated string at `HL`; `$FC66` accepts
one character in `A`. Both target AdamNet device `$02` and retry the
printer-busy response `$86`. The DSK and DDP forms print `AMY` plus CR;
`tools/test-adam-project-forms.mjs` verifies the exact four-byte spool together
with the example's VRAM text and RAM completion signature.

Amy now exposes that verified service as
`print "AMY" to printer status Result` or `print Character to printer`.
`tools/test-native-eos-amy-printer.mjs` independently compiles the Amy source,
boots it from DSK and DDP, and verifies the exact spool, status, and continuation.

`tools/inspect-adam-binary-io.mjs` reports immediate and common indirect Z80
I/O forms, including ports kept in a table and loaded through `LD BC,(nn)`.
Its output is static triage only; runtime tracing is still required before an
interface is treated as confirmed.

## Historical SmartBASIC extensions: Auto-AID and SmartBEST

The downloaded Auto-AID v1 DDP and v2 DSK are structurally valid EOS media.
Both contain the same 5,005-byte `AABINHLPH` machine-language module and the
same readable SmartBASIC validation programs, byte for byte. This independently
proves that one resident extension was distributed unchanged across DDP and
disk rather than being tied to one medium.

Auto-AID's public SmartBASIC ABI uses `CALL 27500` with a parameter block at
`27407` (`$6B0F`). Its supplied tests document at least these functions:

| Function | Parameter contract demonstrated by the supplied test |
| ---: | --- |
| `1` | Keyboard read/poll: delay at `27408`, availability at `27409`, character at `27410`. |
| `2` | Send one character from `27408` to the printer. |
| `3` | Write one or more raw PSG bytes beginning at `27409`; examples implement sweeps, white noise and attenuation. |
| `18-21` | Read/write sprite attributes and patterns using the shared parameter area. |

The sprite example also documents the TMS9918A conventions explicitly: sprite
Y is stored as screen Y minus one, `$FF` represents screen row zero, and bit 7
of the color byte applies the 32-pixel early-clock shift. These are useful
semantic fixtures for Amy's sprite API even though Auto-AID itself is not an
EOS ABI.

Auto-AID is also direct evidence for writable EOS-vector interception. Its
installer saves and replaces the target words inside `$FCA8` (start keyboard
read), `$FC4B` (finish keyboard read), and `$FC66` (printer character), then
restores all three during uninstall. Amy target backends must therefore call
the public EOS vectors, not bypass them by calling the current firmware
implementation addresses. This preserves compatibility with resident drivers
and extensions.

The v2 disk boots successfully in GearColeco to `Coleco SmartBASIC 2.0`.
Its `HELLO` program loads `EXTMEM` and runs the Auto-AID installer. The
installer reserves low memory with `LOMEM:32500`, loads the module at `$6B6C`,
tests for a 64 KiB expansion and can use that expansion as its print buffer.
This reproduces the article's memory-collision warning from the software
itself rather than relying on the review alone.

A 1,400-frame firmware trace observes native EOS file, VDP and asynchronous
keyboard services, plus three calls to OS-7 `$1FBB` (`GET_VRAM`). The disk is
therefore a concrete hybrid EOS+OS-7 application, not a pure-EOS example.

SmartBEST is likewise a SmartBASIC enhancement disk containing a resident
machine module, converter/installer programs and its own modified BASIC image.
VideoTunes contains a 48 KiB music program plus separately named song files.
It is a promising case for reusable data-file workflows.

SmartBEST now has runtime evidence as well. It boots in GearColeco to its cyan
`DATA DOCTOR SmartBEST V1.0` prompt and exercises both firmware families. A
1,200-frame trace reaches EOS block/file, VDP, sound, date and asynchronous
keyboard services, while also calling OS-7 VRAM, sound-table, table-init and
sprite-priority routines. Unlike a simple pure-EOS loader, this is an extensive
hybrid runtime whose resident BASIC environment deliberately retains OS-7
subsystems. It is therefore a strong regression fixture for Amy's hybrid
target and for preventing accidental assumptions that an ADAM application
must use only one firmware family.

VideoTunes now supplies the complementary pure-EOS application case. It boots
in GearColeco to a graphical staff editor with piano keyboard, tempo, key and
title fields. During 1,400 frames it loads its 48 KiB `MUSICPGM` through EOS
and uses EOS file, VDP, keyboard and controller services; no OS-7 public call
was observed. The disk keeps songs such as `SONATA #2`, `RONDINO`, `O CANADA!`
and the 158-byte `MY_SONG` as separate EOS files. This is direct evidence for
an Amy project form consisting of one native executable plus user-editable
document files, rather than embedding every asset into the program image.

`tools/analyze-adam-media.mjs` now supports both interleaved 160 KiB DSK images
and linear block-oriented DDP images. Auto-AID v1 is therefore catalogued by
the same analyzer instead of being reported as an unsupported geometry.

### Chess Champ VDP-memory transition

`Chess Champ (1988) (Digital Express Inc.) [ExpRAM].dsk` prepares its title
VRAM before setting the TMS9918A 16K-memory bit in register 1. ADAM+ 2.0.09.26
preserves that VRAM and shows the title immediately. GearColeco previously
permuted all 16K whenever the bit changed, exposing a corrupted Graphics I
screen until the game rebuilt VRAM. The ADAM/ColecoVision hardware has 16K of
physical VRAM, so the register transition must not move existing bytes.

ADAM+ models media readiness through ten service passes (`DELAY_IO = 10`),
while GearColeco currently models explicit DSK/DDP device latency. Those are
not equivalent timing units, so the media timings remain unchanged until they
can be calibrated independently. `tools/test-chess-champ-adam-compatibility.mjs`
locks the stable loader-title and game-screen frame hashes.
